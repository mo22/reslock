# reslock

Resource lock manager for coordinating shared system resources (GPU VRAM, RAM, CPU) across processes on a single machine. No daemon — all coordination via a JSON state file with file locking.

## Project Structure

- `src/reslock/` — library source
  - `pool.py` — `ResourcePool`, `LeaseHandle`, `EntryHandle` (main API)
  - `models.py` — Pydantic models (`State`, `Lease`, `QueueEntry`, `PoolStatus`) plus the v4 scheduler (`State.try_resolve_request`)
  - `state.py` — file-locked state read/write
  - `detect.py` — system resource detection (GPU VRAM via nvidia-smi/torch, CPU, disk)
  - `nvml.py` — pynvml pre-flight (driver-side free VRAM ground truth, hard-fails on CUDA hosts without pynvml)
  - `audit.py` — GPU orphan diagnosis (PIDs holding VRAM not covered by any lease)
  - `resources.py` — public detection API (re-exports from detect.py)
  - `cleanup.py` — dead-PID lease cleanup
  - `cli.py` — Click CLI (`reslock status`, `reslock run`, etc.)
- `tests/` — pytest tests
- `examples/` — usage examples

## Publishing

Publishing is handled by GitHub Actions (`.github/workflows/publish.yml`). To release:

1. Bump version in `pyproject.toml`
2. Commit and push to main
3. Create a GitHub release with tag `vX.Y.Z` — this triggers trusted publishing to PyPI

Do NOT publish manually with `uv publish` — the project uses PyPI trusted publishing via OIDC.

## Key Design Decisions

- State file default: `/var/lib/reslock/state.json` (system-wide, sticky-bit 1777). Falls back to `~/.reslock/state.json` with a warning if `/var/lib` is not writable. Override with `RESLOCK_DIR` env var. Path selection (in `_default_state_path()`) is side-effect-free; directory creation happens in `ensure_state_file()`.
- File locks are held only during reads/writes, not for lease duration
- `read_state()` uses shared lock (`portalocker "r"`), `transact()` uses exclusive lock (`"r+"`) — read-heavy workloads don't block each other
- Dead processes cleaned up automatically via PID checking; a lease is alive if owner PID OR any child PID in `lease.pids` is alive
- Per-GPU VRAM tracking for multi-GPU systems. **Capacity registration** still uses UUID-based keys: `gpu_{UUID}_vram_mb` (e.g. `gpu_GPU-1a2b3c4d-..._vram_mb`). Keying by the host-stable GPU UUID (not nvidia-smi index) keeps coordination correct across containers with partial GPU mappings — the NVIDIA container runtime renumbers visible devices from 0, but UUIDs are invariant. **Acquire requests** are abstract: uniform `vram_mb_each` + `num_gpus`, or non-uniform per-slot `vram_mb=[...]` (v0.11.0+). The scheduler binds specific UUIDs at promotion time. The lease's `resources` dict stores those resolved UUID-keyed bindings. Consumers that hold a local torch index can still use `reslock.gpu_resource_key(i)` for capacity registration. Compatibility detail: a list passed as `vram_mb` selects the new GPU scheduler path; a single integer `vram_mb=N` remains the pre-existing free-form counter named `vram_mb`.
- State-file schema version: `5`. Bumps:
  - v1 → v2 (v0.5.0): GPU keys switched from index-based to UUID-based.
  - v2 → v3 (v0.8.0): split `Lease` (resource reservation) from `QueueEntry` (work item — queued or active). Work-tracking fields (`estimated_seconds`, `progress`) moved to `QueueEntry`. Acquire request shape changed to `vram_mb_each` + `num_gpus`. Reclaim now skips leases with any active QueueEntry attached.
  - v3 → v4 (v0.11.0): `QueueEntry` gained `vram_mb` for non-uniform per-slot asks. The new field is intentionally a schema bump because v3 readers use `extra="forbid"`; hiding `None` during serialization would only defer the incompatibility until the first real per-slot request. Mixed v3/v4 operation is unsafe. Upgrade all consumers sharing a file at once: stop them, delete `state.json`, install matching reslock versions, and restart so capacities and leases are repopulated under v4.
  - v4 → v5 (v0.12.0): `Lease` gained `reclaim_requested_at`, and **a schema mismatch now raises `SchemaVersionMismatch` instead of silently resetting the file**. Same lockstep rule as every bump — all consumers sharing a file move together.
  - On read, a file whose `version` differs in **either** direction raises `reslock.state.SchemaVersionMismatch`; nothing is written and the file is left byte-identical. Up to v0.11.1 the read returned a fresh empty `State()` instead, which `transact()` then wrote back — one `acquire()` from a stale installation erased every other consumer's leases (VRAM handed out twice, one WARNING as the only trace), and it escalated, because the laggard wrote *its* version and the correct consumers then reset in turn. Failing puts the error on the consumer that can't speak the schema and leaves everyone else running. Upgrade procedure unchanged: stop all consumers on the host, `reslock reset --force` (or delete `state.json`), redeploy with matching versions, restart.
    - Note on reach: this only protects against mismatches produced *after* every consumer runs ≥0.12.0. A pre-0.12.0 laggard still resets the file; what changes is that the up-to-date consumers then refuse instead of re-registering and double-allocating — a loud stop needing `reslock reset --force`, not silent corruption.
    - `peek_state_version(path)` reads just the version field without validating the rest, for monitors and `reslock status` that must report on a file they may not speak. `force_reset_state(path)` rewrites at the current schema without reading — the supported recovery, and destructive by design (capacities go too, so only with all consumers stopped).
    - CLI: any command against a foreign schema prints both versions and exits **3** (`SCHEMA_MISMATCH_EXIT_CODE`), no traceback.
- v4 scheduler: spread placement. GPU asks are sorted descending (the uniform form expands to repeated equal asks), GPUs are sorted by effective free VRAM descending (ties broken by UUID), then paired. If any ask exceeds its paired GPU, no assignment exists. This pairing is optimal for feasibility and retains the most-free-first policy.
- Priority queue determines which waiter gets resources next. The priority gate also requires the higher-priority entry would actually fit on the next tick (internal accounting + NVML cross-check on the GPUs the scheduler would pick) — otherwise an NVML-short waiter would silently block lower-priority non-GPU waiters.
- `Lease.reclaim_requested_at` (v0.12.0) records when `reclaim_requested` flipped to `True`, stamped only on the `False→True` transition in `_request_reclaim_to_resolve` (pool.py, the single write site). Re-stamping would be a bug, not a refresh: that function runs on every poll tick of every waiter, so it would keep a nine-day-old pending reclaim reading as milliseconds old — see the 2026-08-01..10 incident, a llama-server lease sitting on two GPUs with a pending reclaim for nine days. `acquired_at` is no substitute (a long-lived lease reclaimed ten seconds ago would look ancient). `None` means "unknown", i.e. a lease flipped before the upgrade — `reslock status` / `top` render the age only when it is known, never as `0s`. External monitors should prefer this field over their own first-observation bookkeeping.
- Reclaimable leases allow preemption by higher-priority work. Reclaim **skips** leases that have any active `QueueEntry` attached — consumers cooperatively mark leases busy via `lease.start_work(...)` for the duration of in-flight requests, and the scheduler won't try to evict them. The busy state is implied by entry attachment (no separate `Lease.busy` field).
- Work tracking model: a `QueueEntry` represents a unit of work, queued or actively running. On promotion the entry stays in `state.queue` with `lease_id` and `started_at` set (`is_active == True`). Two ways to create an attached entry:
  - **Auto-track**: `pool.acquire(estimated_seconds=N)` keeps the queueing entry attached to the new lease. `LeaseHandle.entry` exposes the `EntryHandle`. Auto-completed on `lease.release()`.
  - **Per-request**: `lease.start_work(estimated_seconds=M)` creates a new attached entry for one inference call on a persistent reclaimable lease (e.g. aiserver's model-load lease). Caller-managed: explicit `entry.complete()` or `with` block.
  - Peers walking `pool.status().queue` see all active work with optional `estimated_seconds` / `progress`. `Lease.acquired_at` is meaningless for ETA on long-lived leases — peers should compute `entry.estimated_seconds * (1 - entry.progress)` or `(now - entry.started_at)` deltas instead.
- NVML pre-flight (`nvml.py`): on every GPU acquire, reslock reads driver-reported free VRAM via pynvml and cross-checks the scheduler's picked GPUs. If the driver disagrees with internal lease accounting (typically because a process holds VRAM without a registered lease — see SCRIBA-325), reslock either refuses (`try_acquire`) or signals reclaim on its own opportunistic leases (`acquire`). Hard-fails on a CUDA host without pynvml — silent fallback would defeat the cross-check. Cache window 1s. Non-GPU acquires never touch pynvml (the `cuda` extra is optional). Reclaim cascades to exhaustion when NVML drift is involved (`partial=True`): we evict every reclaimable that contributes, even if the union won't fully cover the gap, since the residual may be an external (unaccounted) consumer that's about to leave.
- `reslock.audit.gpu_orphans(state)` (v0.8.0+): diagnostic primitive that returns PIDs holding VRAM (per `nvidia-smi --query-compute-apps`) that aren't registered with any active lease. Reslock itself never terminates orphans — that policy belongs in the consumer (e.g. aiserver's `gpu_audit.py`). Exposed as `pool.gpu_orphans()` for convenience.
- `LeaseHandle.shrink()` doesn't need its own scheduler hook — waiters in `_acquire_blocking` / `acquire_async` already poll `_try_promote()` every `poll_interval`, so freed capacity is picked up naturally (same as `release()`).
- `Lease.queued_at` / `Lease.wait_sec` are stamped at promotion time so consumers can split "queued behind reslock" from "running on GPU" without timing the acquire themselves. `try_acquire` records `wait_sec=0.0` (no queue path); `_try_promote` computes `acquired_at - queued_at`. `LeaseHandle.gpu_uuids` and `LeaseHandle.gpu_torch_indices` derive GPU device lists from the lease's `gpu_{uuid}_vram_mb` resolved bindings (the latter is empty when CUDA/torch isn't available).
- First-class CPU/RAM (v0.9.0, for kirk CPU-LLM serving): `cpu_cores` / `ram_mb` are the standard counter keys (constants `CPU_CORES_KEY` / `RAM_MB_KEY` in `detect.py`), with explicit kwargs on `acquire()` / `try_acquire()` / `acquire_async()` that fold into the non-GPU demand dict (`_fold_first_class`, rejects ≤ 0). Capacity detection: `detect_cpu_cores()` (affinity-aware) and `detect_ram_mb(reserve_mb=...)` (`/proc/meminfo` capped by cgroup v1/v2 limits on Linux, `sysctl hw.memsize` on macOS; raises if the reserve leaves no capacity). Queue/priority/reclaim semantics are the existing counter machinery — covered in `tests/test_cpu_ram_resources.py`. The feature was purely additive and did not cause the then-current v3 schema bump. NUMA is deferred: keys stay host-global, but the naming reserves `cpu_cores@node<N>` / `ram_mb@node<N>` for a v2 per-node design (free-form string keys make that additive too). Non-GPU acquires still never touch pynvml.
- Disk leases (v0.10.0) use **free-space admission**, not registered capacity: `acquire(disk_mb=16_384, disk_path="/data")` → key `disk_mb@<mount>` (helpers `disk_mb_key`/`parse_disk_mb_key`); granted only while `request + sum(active disk leases on the mount) <= actual free` per live statvfs (`get_disk_free_mb`, re-read every poll tick — the disk analog of the NVML pre-flight). Contract: reserve → write the bytes → release; written bytes then show in statvfs itself, so persistent storage needs no long-lived lease (PID-based cleanup would drop it anyway). During a write the holder's landed bytes are double-counted (conservative); `shrink()` returns headroom incrementally. Unstattable `disk_path` raises at acquire (typo shouldn't queue forever); gate entries with unstattable paths are treated as 0-free (don't block others). `reslock status` renders a per-mount "Disk (free-space leases)" table; `reslock run --disk 16G --disk-path /data`. The `disk_mb=` kwarg repurpose is why the shrink tests' arbitrary counter was renamed `scratch_mb`. `detect_disk_mb()` (static totals) kept for custom schemes.
- GPU detection order (v0.11.1): `detect_gpu_vram_mb()` tries `detect_gpu_vram_mb_cuda_driver()` (ctypes against `libcuda.so.1` / `nvcuda.dll`) before torch and nvidia-smi. Two reasons, both measured on kirk 2026-08-12: (1) **the torch step breaks the caller's fork.** `torch.cuda.is_available()` opens 12 `/dev/nvidia*` fds, and a process holding those can no longer fork a CUDA-capable child ("CUDA driver initialization failed"). No CUDA *context* is created by any detection path — that was ruled out separately; the damage is the open device files. (2) torch builds without `get_device_properties().uuid` (e.g. 2.0.0) return `{}` and silently fall through to nvidia-smi, so the registered capacity depended on the consumer's torch version — 24135 under torch 2.10, 24576 under torch 2.0, same host. Branch logic: fork the read into a short-lived child **only** on Linux when CUDA isn't open yet (~250 ms, parent stays fork-safe); read directly otherwise — Windows has no fork to protect, and a process that already has CUDA open is committed anyway (~0.2 ms, `cuInit` is then a no-op). `_cuda_driver_initialized()` uses open `/dev/nvidia*` fds, which is an exact discriminator; libcuda in `/proc/self/maps` is **not** (already true after a bare `import torch`). The child result comes back as `key=value` lines over a pipe with a `select` timeout, so a wedged child degrades to `{}` instead of hanging startup. Tests: `tests/test_cuda_driver_detect.py` (branch selection, fd probe and fork plumbing are covered without a GPU; the actual libcuda read is not).
- Capacity tripwire (v0.10.1): `set_resources()` warns (log-only, never clamps/refuses) when a GPU VRAM capacity is registered below — or above — the NVML `memory.total` for that UUID (`_warn_gpu_capacity_mismatch`). Since v0.11.1 the below-direction has a tolerance band (`GPU_CAPACITY_MIN_RATIO = 0.95`): the CUDA driver legitimately reports less than the physical total, so an exact comparison fired on every correctly configured CUDA host — ten WARNINGs per consumer start on kirk, and per `set_resources` call, which some consumers make every ~2 s. A tripwire that is always tripped is not one. Measured gaps: 1.8 % on Linux (24135 of 24576 MB), 0.004 % on Windows/WDDM (24575 of 24576); the 2026-07-20 incident sat 27 % low. The gap is neither constant nor proportional across driver models, hence a ratio rather than a fixed MB allowance. Tolerated offsets still log at DEBUG. Above the total there is no tolerance. Guards against consumers persisting derived free-based snapshots as capacity (kirk incident 2026-07-20: a stale ~18 GB/card snapshot blocked a 10x19 GB acquire on an idle host). Capacity = physical total; transient usage is the NVML pre-flight's job at placement time. Fails soft without NVML; `nvml_total_vram_mb()` caches totals for the process lifetime (set_resources can be called every ~2 s by legacy consumers). Tests: `tests/test_set_resources_guard.py`.
- v3 hard-cut: `LeaseHandle.update()` no longer accepts `estimated_seconds` / `progress` (TypeError) — those moved to `EntryHandle.update()` on the attached entry. `pool.acquire(gpu_<uuid>_vram_mb=N)` keys are rejected — use `vram_mb_each` + `num_gpus` or, on v0.11.0+, `vram_mb=[...]` instead. Capacity registration via `set_resources()` still uses UUID-keyed entries. Coordinated consumer bump (scriba, aiserver, kirk-rpcserver) required at v0.8.0.

## Platform compatibility

- `resource` (POSIX stdlib) is imported with `try/except ImportError` in `detect.py` — Windows doesn't ship it. `get_self_rss_mb()` and `get_self_cpu_seconds()` return `None` when it's absent; downstream `get_self_actual_resources()` already handles `None` RSS. Regression covered in `tests/test_windows_compat.py` by mocking `builtins.__import__` + `importlib.reload(reslock.detect)` — runs on Linux/macOS CI without needing a Windows runner.
- Windows consumers (scriba on-prem installs — SCRIBA-308) require `reslock>=0.4.1`.
